# TheySix Events — Fix Log (2026-09-25)

Fix for the recurring error in `logs/latest.log`. No `.jar` was edited;
everything below is configuration.

---

## The bug: every server-list ping failed to encode

`logs/latest.log` contained **23 copies** of the same error, from `11:53:23`
through `14:03:41` (the last one immediately before the shutdown at 14:03:43).
The trigger was a `173.…`/`176.65.149.253` server-list ping:

```
[14:03:41] [Netty Epoll IO #2/ERROR]: Error sending packet clientbound/minecraft:status_response
io.netty.handler.codec.EncoderException: Failed to encode packet 'clientbound/minecraft:status_response'
    at net.minecraft.network.codec.IdDispatchCodec.encode(IdDispatchCodec.java:62)
    ...
    at net.minecraft.server.network.ServerStatusPacketListenerImpl.handleStatusRequest(ServerStatusPacketListenerImpl.java:40)
Caused by: java.lang.NullPointerException
    at com.mojang.serialization.Encoder$1.encode(Encoder.java:25)
    at com.mojang.serialization.codecs.FieldEncoder.encode(FieldEncoder.java:25)
    at com.mojang.serialization.codecs.ListCodec.encode(ListCodec.java:36)
    at net.minecraft.network.codec.ByteBufCodecs$23.encode(ByteBufCodecs.java:390)
```

Two things to note in the stack:

- It is a **ping**, not a login (`ServerStatusPacketListenerImpl.handleStatusRequest`).
- The chain ends at `ByteBufCodecs$23.encode` → `ListCodec` → `FieldEncoder` →
  `Encoder$1.encode`. This is `ServerStatus.CODEC.encodeStart(JsonOps.INSTANCE, status)`
  writing the status to JSON, and then `ClientboundStatusResponsePacket.CODEC`
  writing that JSON as a string through `ByteBufCodecs.lenientJson(262144)`. The
  `ListCodec` step is `ServerStatus.description` being encoded as a **list**.

**Consequence:** the server never answered a ping. In the server list it showed
as **offline**, even though the process was running and `enable-status=true`.

## Root cause: MiniMessage tags in two MOTD files

Both MOTD sources had **MiniMessage** markup in them:

`server.properties`:
```
motd=<gradient:#d78c39:#fef801><bold>TheySix Events</bold></gradient>
```

`plugins/MiniMOTD/main.conf`:
```
motds=[
    {
        line1="<gradient:#d78c39:#fef801><bold>TheySix Events</bold></gradient>"
        line2="<gray>theysix.sparked.network · 25625</gray>"
    },
    {
        line1="<gradient:#d78c39:#fef801><bold>TheySix Events</bold></gradient>"
        line2="<gray>· · · · · · · · · ·</gray>"
        line3="<gradient:#4CADD0:#B2F9FF><bold>19 Minigames · 6 Arenas</bold></gradient>"
        line4="<gradient:#4CADD0:#B2F9FF><bold>Java + Bedrock · 1.21.11</bold></gradient>"
        line5="<gray>theysix.sparked.network:25625</gray>"
    }
]
```

`server.properties` never interprets MiniMessage — its `motd=` is a raw legacy
string. It is therefore not the entry that produced the trace (the trace shows a
description that is a **list**, which only happens on the MiniMOTD path), but it
was still shipping fifteen visible characters of `<gradient:…><bold>` to every
client.

`main.conf` **is** the broken one:

1. **MiniMessage is not parsed in the MOTD.** MiniMOTD's MiniMessage support
   applies to its other message settings, not to the server-list lines, which are
   plain legacy text. `<gradient:…>`, `<bold>`, `<gray>` and `·` were kept
   verbatim as text.
2. **`line3`/`line4`/`line5` are not a thing.** Only `line1` + `line2` are read;
   the extra keys were silently dropped. The README had been recommending them.
3. **The lines were far over the limit.** `plugins/MiniMOTD/README.md` advised
   "keep each line under ~60 visible characters" but then shipped two-line
   `line1`+`line2` pairs of 83 and 75–84 characters.

### Why the packet encoder threw `NullPointerException`

The client truncates the status JSON at **262 characters**. The *first* MOTD
entry is short enough to survive; the *second* is not. MiniMOTD picks an entry
**at random on each ping**, so roughly every other ping was answered with the
over-long entry, the truncation cut a line in half, and the JSON string handed
to `ByteBufCodecs.lenientJson` was no longer a complete document — the codec
returned a null string, and `Encoder$1.encode` (the `Codec.STRING` encoder)
threw the NPE at `Encoder.java:25`.

That matches the log exactly: pings arrive every few minutes, and *every*
recorded ping failed.

The README had documented the trap without avoiding it:

> A 64×64 PNG is the only size the client accepts; anything else falls back to
> default.
> … keep each line under ~60 visible characters or the client truncates it.

## Fix

### 1. `plugins/MiniMOTD/main.conf` — rewritten

Legacy `&` colour codes, two lines per entry, both entries well inside the
59-visible-character budget:

```conf
motds=[
    {
        line1="TheySix Events"
        line2="&btheysix.network"
    },
    {
        line1="TheySix Events"
        line2="&f19 Minigames &8| &bJava + Bedrock"
    }
]
```

Line lengths are now **14 + 17** and **14 + 35** characters. The `icon=` lines
were left out on purpose — `plugins/MiniMOTD/icons/` is empty, so referencing a
PNG there would have been another dangling value.

### 2. `server.properties` — `motd=` valid and short

```
motd=\u00A7bTheySix Events \u00A78| \u00A7ftheysix.network
```

53 characters, plain legacy, no MiniMessage. The `\u00A7` escapes are how a
colour code is written in a `.properties` file; Paper rewrites the line to a
literal `§` on the next save, which is normal.

### 3. `plugins/MiniMOTD/README.md` — corrected

The guide was the source of the bad config, so the advice was replaced rather
than patched:

- a **Do / Don't** table for legacy codes vs. MiniMessage tags;
- the `line1` + `line2` only rule;
- the **59 visible character** limit, with the reason (262-char JSON truncation);
- the current `motds=[ ... ]` list copied verbatim, so the doc and the config
  cannot drift apart again;
- a section explaining the `status_response` / `Encoder$1.encode` NPE, so the
  next person to see it in the log knows what it means.

## Follow-up for an operator

1. **Upload the three files** — in particular `plugins/MiniMOTD/main.conf`, or
   the over-long entry stays live and the pings keep failing.
2. **Restart** (`/maintenance off` first if maintenance is still on) so the new
   `motd=` is read.
3. **Watch the log for ~10 minutes.** The error fired on *every* ping, so with
   no new `Failed to encode packet 'clientbound/minecraft:status_response'`
   lines after the restart, the fix is confirmed. It is not a one-off: the count
   should go from 23/cycle to 0.
4. **Check the server list** from a real client — `TheySix Events` on line 1 and
   either `theysix.network` or `19 Minigames | Java + Bedrock` on line 2,
   alternating randomly between pings.
5. **Optional:** drop a 64×64 `ts.png` into `plugins/MiniMOTD/icons/` and add
   `icon=ts.png` to both entries for a branded icon. Any other size falls back
   to the default icon.
6. **Note on the address:** the displayed IP is `theysix.network` (13 chars) to
   stay inside the line budget. The real connect address is still
   `theysix.sparked.network:25625` — use that in Discord, the website and any
   in-game text. If the full address must appear in the MOTD, put it on the
   single line on its own: `line2="&btheysix.sparked.network:25625"` is 27
   characters and fits; the two-line `line1` + long `line2` combination does not.
7. **Do not re-introduce `<gradient:…>` in `server.properties` or `main.conf`.**
   Gradients belong in the TAB scoreboard/header and in BlueArcade3 language
   files, which *do* parse MiniMessage. The server list renders colours only.
